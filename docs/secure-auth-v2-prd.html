1. Why This Was Built — Security Vulnerabilities 1. Ye System Kyun Banaya — Security Problems Jo The

Before v2.0, the authentication had two critical flaws that allowed unauthorized access to the dashboard and platform.

v2.0 se pehle, authentication mein do badi problems thi jo bina permission ke dashboard access karwa deti thi.

Vulnerability 1 — Cookie Forgery Attack Vulnerability 1 — Fake Cookie Se Dashboard Access

What happened: The frontend was checking whether a cookie (e.g. t = any value) existed to decide whether to show the dashboard layout, module names, and route structure. No real token validation was happening on the client side.

Kya hua: Frontend cookie ki existence check karta tha (jaise t = kuch bhi). Agar cookie thi, dashboard show ho jaata tha — chahe token valid ho ya na ho. Koi real validation nahi tha client side pe.

Attack: Anyone who opened browser DevTools → Application → Cookies → added t = hello could see the full dashboard structure, all module names, and all route paths without ever logging in.

Attack kaise hota tha: Koi bhi DevTools → Application → Cookies mein jaake t = hello set kar deta, aur poora dashboard structure, module names, aur routes dikh jaate — bina login kiye.

Impact: Information disclosure of the entire application structure to unauthenticated users.

Nuksan: Bina login kiye koi bhi poori application ki structure dekh sakta tha.

Vulnerability 2 — Cookie Theft via Extension Vulnerability 2 — Cookie Editor Extension Se Session Chori

What happened: The JWT token was stored in a readable cookie (not HTTP-only). Browser extensions like "EditThisCookie" or "Cookie Editor" could read its full value.

Kya hua: JWT token ek normal (readable) cookie mein tha. "EditThisCookie" ya "Cookie Editor" jaise browser extension se koi bhi uski value padh sakta tha.

Attack: User A logs in → copies their JWT cookie value → pastes it into another browser or gives it to someone → that person gets full access to User A's account with no password needed.

Attack kaise hota tha: User A login karta → extension se apni JWT cookie copy karta → doosre browser mein paste → doosra banda User A ka poora account access kar leta — bina password ke.

Impact: Full account takeover. Tokens lived for 7 days, so the stolen session was valid for up to 7 days.

Nuksan: Poora account takeover ho sakta tha. Token 7 din tak valid tha, matlab chori hua session bhi 7 din chalega.

How v2.0 Fixes Both v2.0 Mein Dono Ko Kaise Fix Kiya

  • Access token in memory only — frontend stores it in JS state, never in a cookie. No cookie to fake or steal.
  • Refresh token in HTTP-only cookie — JavaScript (and extensions) cannot read it. Not visible in DevTools either.
  • Server-side session — even if a refresh token is somehow leaked, logout invalidates the session in the database immediately.
  • CSRF token — an extra secret per-session token sent in a header, so cross-site requests cannot work even if the HTTP-only cookie is sent automatically.
  • Access token sirf memory mein — frontend JS state mein rakhta hai, cookie mein nahi. Fake karne ko kuch hai hi nahi.
  • Refresh token HTTP-only cookie mein — JavaScript ya extension is cookie ko padh hi nahi sakta.
  • Server-side session — logout hote hi DB mein session invalid ho jaata hai. Chora hua token bhi kaam nahi karega.
  • CSRF token — ek extra secret jo header mein bheja jaata hai, cross-site attack nahi ho sakti.

Important — Refresh Token Rotation Important — Refresh Token Rotation

Every call to /auth/refresh generates a completely new refresh token and CSRF token, and immediately invalidates the old session. This means if an attacker intercepts an old refresh token, it will already be invalid by the time they try to use it.

Har /auth/refresh call par naya refresh token aur CSRF token banta hai, aur purana session turant invalid ho jaata hai. Iska matlab: agar koi purana token le bhi le, tab tak wo invalid ho chuka hoga.

5. Merits & Demerits — Honest Analysis 5. Faide aur Nuksan — Honest Analysis

✅ Merits (What This Gets Right) ✅ Faide (Kya Theek Hai)
  • Cookie forgery is impossible: Access token is in memory — there is no cookie to fake. Setting any random cookie does nothing.
  • Fake cookie attack impossible: Access token memory mein hai — fake karne ko cookie hai hi nahi.
  • Session theft is nearly impossible: Refresh token is HTTP-only — extensions cannot read it, and it's stored as a hash in DB so even a DB leak doesn't expose raw tokens.
  • Session chori lagbhag impossible: Refresh token HTTP-only hai — extension padh nahi sakta. DB mein hash hai, toh DB leak se bhi raw token nahi milega.
  • Instant logout: is_valid = false in DB means the session is dead even if the access token hasn't expired yet. Next request will be rejected in Step 2 of the middleware chain.
  • Instant logout: DB mein is_valid = false set ho jaata hai. Chahe access token 15 min ke andar expire na hua ho, agla request Step 2 par hi reject hoga.
  • CSRF protected: Even if an attacker tricks the browser into making a cross-site POST, they can't provide the x-csrf-token header (it's in memory, not a cookie), so the request fails.
  • CSRF protected: Agar koi browser ko cross-site POST karwa bhi de, wo x-csrf-token nahi de sakta (wo memory mein hai, cookie mein nahi).
  • Token rotation: Every refresh invalidates the old session. Replay attacks with old refresh tokens are impossible.
  • Token rotation: Har refresh par purana session invalid. Purane tokens se replay attack nahi ho sakta.
  • Short-lived access tokens (15 min): Even if somehow intercepted (e.g. server logs), they expire quickly.
  • Short-lived access tokens (15 min): Agar kisi ne intercept bhi kar liya, 15 minute mein expire ho jaayega.
  • SameSite=Strict cookie: The refresh token cookie is never sent on cross-site requests — even without CSRF protection it would be partially safe.
  • SameSite=Strict cookie: Refresh token cookie cross-site requests mein send hi nahi hoti.
  • Zero-trust user status: Every request re-checks if the user is still active in DB. Admin can deactivate a user mid-session.
  • Zero-trust user status: Har request mein user active hai ya nahi DB se check hota hai. Admin mid-session deactivate kar sakta hai.
  • Auto-cleanup: MongoDB TTL index deletes expired sessions automatically — no cron job needed.
  • Auto-cleanup: MongoDB TTL se expired sessions apne aap delete — koi cron job nahi chahiye.
⚠️ Demerits (Trade-offs & Risks) ⚠️ Nuksan (Trade-offs aur Risks)
  • More DB queries per request: Auth middleware now makes 2 DB queries per request (session + user) instead of 1. At scale, this adds latency — mitigatable with Redis session cache.
  • Zyada DB queries: Har request mein ab 2 DB queries (session + user) hoti hain. Scale par latency badh sakti hai — Redis se fix ho sakta hai.
  • Frontend memory is volatile: If the user closes the tab/browser, the access token and CSRF token are lost. The refresh token cookie survives (browser saves cookies), so the user can silently re-auth — but only if the frontend handles this on app load.
  • Memory volatile hai: Tab close karo, access token aur CSRF token gone. Refresh cookie survive karti hai, par frontend ko app load par silent refresh handle karna hoga.
  • Multiple tabs / devices: Each login creates a new session. Multiple open tabs share the same access token only if stored in a shared state (e.g. React context that all tabs read). Otherwise, each tab must refresh independently.
  • Multiple tabs: Har login naya session banata hai. Multiple tabs mein access token share karna frontend ki responsibility hai.
  • No "remember me" feature: Refresh token expires after 7 days regardless. Long-term sessions would need configurable expiry.
  • "Remember me" nahi: Refresh token 7 din mein expire ho jaata hai. Long-term session ke liye configurable expiry chahiye hoga.
  • HTTPS required in production: The secure cookie flag is on in production. If the server runs HTTP (not HTTPS), the refresh cookie won't be sent. This is the right behavior — but requires HTTPS infrastructure.
  • Production mein HTTPS zaruri: Production mein secure flag on hai. HTTP par refresh cookie send nahi hogi. HTTPS infrastructure chahiye.
  • Session DB dependency: If the sessions MongoDB collection is unavailable, all authenticated requests will fail (session lookup fails). A Redis fallback would make this more resilient.
  • Session DB pe dependency: Agar sessions collection unavailable ho, sab authenticated requests fail ho jaayenge. Redis fallback se zyada resilient banaya ja sakta hai.
  • No multi-device logout: Logging out on one device only invalidates that device's session. "Logout everywhere" would require invalidating all sessions for a user_id.
  • Multi-device logout nahi: Ek device par logout sirf us device ka session invalid karta hai. "Sab jagah logout" ke liye sab sessions invalid karne honge.
Future Improvements Future mein Kya Improve Ho Sakta Hai
  • Add Redis as session cache to reduce MongoDB load on auth middleware
  • Add "logout all devices" endpoint — Session.updateMany({ user_id, is_valid: true }, { is_valid: false })
  • Track multiple active sessions per user and show them in a "Manage Sessions" page
  • Add suspicious login detection (new country / IP mismatch)
  • Redis se session cache banao — MongoDB load kam hogi auth middleware par
  • "Sab devices logout" endpoint add karo
  • User ke sab active sessions track karo aur "Sessions Manage" page banao
  • Suspicious login detect karo (naya country / IP mismatch)

7.1 New Protected Route Checklist 7.1 Naye Route ka Checklist

Every time you create a new route file that needs authentication, follow this checklist exactly:

Jab bhi naya route file banao jo authentication chahta ho, ye checklist follow karo:

  • Import authMiddleware and csrfMiddleware from '../../middlewares'
  • authMiddleware aur csrfMiddleware import karo '../../middlewares' se
  • Apply router.use(authMiddleware, csrfMiddleware, apiKeyMiddleware) — in this exact order
  • router.use(authMiddleware, csrfMiddleware, apiKeyMiddleware) — isi exact order mein
  • NEVER put csrfMiddleware before authMiddleware — CSRF middleware needs req.sessionCsrfToken which is set by auth middleware
  • csrfMiddleware ko authMiddleware se pehle mat daalo — CSRF middleware ko req.sessionCsrfToken chahiye jo auth middleware set karta hai
  • For public routes (no auth needed), do NOT apply any of these middlewares
  • Public routes ke liye (no auth) koi middleware mat daalo
  • Add the new route file to src/routes/index.ts
  • Naya route file src/routes/index.ts mein add karo
  • Run npx tsc --noEmit to confirm zero TypeScript errors before committing
  • Commit se pehle npx tsc --noEmit chalaao — zero errors honi chahiye

7.2 Standard Route Template 7.2 Standard Route Template 

// src/routes/my-feature/my-feature.routes.ts
import { Router } from 'express';
import {
  authMiddleware,
  csrfMiddleware,
  apiKeyMiddleware,
  requirePermission,
} from '../../middlewares';
import { getAll, getById, create, update, remove } from '../../controllers/my-feature.controller';

const router = Router();

// All routes in this file require: valid JWT + valid session + CSRF (for writes) + valid API key
router.use(authMiddleware, csrfMiddleware, apiKeyMiddleware);

router.get('/',     requirePermission('my_feature', 'view'),   getAll);
router.get('/:id',  requirePermission('my_feature', 'view'),   getById);
router.post('/',    requirePermission('my_feature', 'create'), create);   // CSRF auto-checked
router.patch('/:id', requirePermission('my_feature', 'edit'),   update);   // CSRF auto-checked
router.delete('/:id',requirePermission('my_feature', 'delete'), remove);   // CSRF auto-checked

export default router;

// authStore.ts — using Zustand (or use React context / Redux)
import { create } from 'zustand';

interface AuthState {
  accessToken:  string | null;
  csrfToken:    string | null;
  user:         object | null;
  setTokens:    (accessToken: string, csrfToken: string, user: object) => void;
  clearTokens:  () => void;
}

export const useAuthStore = create<AuthState>((set) => ({
  accessToken:  null,
  csrfToken:    null,
  user:         null,
  setTokens:    (accessToken, csrfToken, user) => set({ accessToken, csrfToken, user }),
  clearTokens:  () => set({ accessToken: null, csrfToken: null, user: null }),
}));

// login.ts — call this on form submit
export async function loginUser(email: string, password: string) {
  const res = await fetch('/api/v1/auth/login', {
    method:      'POST',
    credentials: 'include',   // ← required so the rt cookie is received and stored
    headers:     { 'Content-Type': 'application/json' },
    body:        JSON.stringify({ email, password }),
  });
  const { data } = await res.json();
  // Store ONLY in memory — never localStorage
  useAuthStore.getState().setTokens(data.accessToken, data.csrfToken, data.user);
}

8.3 Axios Interceptor — Silent Token Refresh 8.3 Axios Interceptor — Silent Token Refresh 

// apiClient.ts
import axios from 'axios';
import { useAuthStore } from './authStore';

const api = axios.create({ baseURL: '/api/v1', withCredentials: true }); // withCredentials sends the rt cookie

// Attach access token + CSRF token before every request
api.interceptors.request.use((config) => {
  const { accessToken, csrfToken } = useAuthStore.getState();
  if (accessToken) config.headers['Authorization'] = `Bearer ${accessToken}`;
  const method = config.method?.toUpperCase();
  if (csrfToken && ['POST','PUT','PATCH','DELETE'].includes(method ?? ''))
    config.headers['x-csrf-token'] = csrfToken;
  return config;
});

let isRefreshing = false;
let refreshQueue: Array<(token: string, csrf: string) => void> = [];

// Handle 401 — silently refresh and retry
api.interceptors.response.use(
  (res) => res,
  async (error) => {
    const original = error.config;
    if (error?.response?.status !== 401 || original._retry) return Promise.reject(error);
    original._retry = true;

    if (isRefreshing) {
      return new Promise((resolve) => {
        refreshQueue.push((token, csrf) => {
          original.headers['Authorization'] = `Bearer ${token}`;
          original.headers['x-csrf-token']    = csrf;
          resolve(api(original));
        });
      });
    }
    isRefreshing = true;
    try {
      // rt cookie is sent automatically — no body needed
      const { data } = await axios.post('/api/v1/auth/refresh', {}, { withCredentials: true });
      const { accessToken, csrfToken } = data.data;
      useAuthStore.getState().setTokens(accessToken, csrfToken, useAuthStore.getState().user);
      refreshQueue.forEach((cb) => cb(accessToken, csrfToken));
      refreshQueue = [];
      return api(original);
    } catch {
      useAuthStore.getState().clearTokens();
      window.location.href = '/login'; // session fully expired
    } finally { isRefreshing = false; }
  }
);

8.4 Protected Route Guard (React Router) 8.4 Protected Route Guard (React Router) 

// ProtectedRoute.tsx
import { useEffect, useState } from 'react';
import { Navigate } from 'react-router-dom';
import { useAuthStore } from './authStore';
import api from './apiClient';

export function ProtectedRoute({ children }) {
  const { accessToken, setTokens } = useAuthStore();
  const [loading, setLoading] = useState(!accessToken);

  useEffect(() => {
    // On page refresh: access token is gone from memory — try silent refresh first
    if (!accessToken) {
      axios.post('/api/v1/auth/refresh', {}, { withCredentials: true })
        .then(({ data }) => setTokens(data.data.accessToken, data.data.csrfToken, data.data.user))
        .catch(() => {}) // will redirect via the isAuthenticated check below
        .finally(() => setLoading(false));
    }
  }, []);

  if (loading) return <div>Checking session...</div>;
  if (!accessToken) return <Navigate to="/login" replace />;
  return children;
}
Critical — NEVER guard routes by checking a cookie value Critical — Cookie value check karke route guard mat karo

The old vulnerability was exactly this. If you check document.cookie.includes('t=') or any cookie value to show/hide the dashboard, it defeats the entire security system. Route guards MUST call a real API endpoint and check the response.

Purani vulnerability yahi thi. Agar document.cookie.includes('t=') check karke dashboard show karte ho, toh poora security system bekaar hai. Route guard ko real API call karni chahiye aur response check karna chahiye.
