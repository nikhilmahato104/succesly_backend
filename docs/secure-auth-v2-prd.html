Secure Auth v2.1Section 1 · Security Vulnerabilities

1. Why This Was Built — Security Vulnerabilities 1. Ye System Kyun Banaya — Pehle Kya Problems Thi

Before v2.0, the authentication had two critical flaws that allowed unauthorized access to the dashboard and platform.

v2.0 se pehle, authentication mein do badi problems thi jo bina permission ke dashboard access karwa deti thi.

Vulnerability 1 — Cookie Forgery AttackVulnerability 1 — Fake Cookie Se Dashboard Access

What happened: The frontend checked whether a cookie (e.g. t = any value) existed to show the dashboard. No real token validation happened on the client.

Kya hua: Frontend cookie ki existence check karta tha (t = kuch bhi). Agar cookie thi, dashboard show ho jaata tha bina real validation ke.

Attack: Anyone opening DevTools → Application → Cookies → set t = hello → could see all module names, routes, and dashboard structure without logging in.

Attack: Koi bhi DevTools mein jaake t = hello set kare, poora dashboard structure dikh jaata — bina login kiye.

Vulnerability 2 — Cookie Theft via Browser ExtensionVulnerability 2 — Cookie Editor Extension Se Session Chori

What happened: The JWT was stored in a readable cookie. Browser extensions like "Cookie Editor" could copy the JWT value from one browser and paste it into another to hijack the active session.

Kya hua: JWT ek readable cookie mein tha. "Cookie Editor" extension se koi bhi JWT copy karke doosre browser mein paste karta aur session hijack ho jaata.

Impact: A logged-in user's session could be stolen from any machine that accessed the site. Logout had no server-side effect — the stolen token would still work until it expired.

Nuksan: Kisi bhi machine ka session chura sakte the. Logout bhi kaam nahi karta tha — stolen token expiry tak kaam karta rehta tha.

How v2.0/v2.1 Fixes Bothv2.0/v2.1 Ne Kaise Fix Kiya

  • HTTP-only cookie for refresh token — JavaScript and extensions cannot read it.
  • HTTP-only cookie refresh token ke liye — JavaScript aur extensions read nahi kar sakte.
  • Access token in JS memory only — not in any cookie or localStorage, gone on page refresh.
  • Access token sirf JS memory mein — kisi cookie ya localStorage mein nahi, page refresh pe gone.
  • Server-side sessions — every request validates the session in MongoDB. Logout immediately invalidates it.
  • Server-side sessions — har request MongoDB se session validate karti hai. Logout pe turant invalid.
  • CSRF token — required on every state-changing request. Stored in memory, not cookie, so cross-site attacks can't use it.
  • CSRF token — har POST/PUT/PATCH/DELETE pe required. Memory mein hai, cookie mein nahi, toh cross-site attacks nahi chalte.

3.2 Server-Side Session Model (MongoDB)

// sessions collection — one document per login
{
  user_id:             ObjectId,
  refresh_token_hash:  "sha256(rawToken)",  // raw token never stored
  csrf_token:          "64 hex chars",
  expires_at:          Date,               // TTL index auto-deletes
  is_valid:            true,               // set false on logout
  user_agent:          "Mozilla/5.0...",
  ip_address:          "1.2.3.4"
}

3.3 Login Flow

User sends email+password
→
Validate Joi schema
→
Check DB: user exists, is_active
→
bcrypt compare password
→
Generate 3 tokens
→
Create session in DB
→
Set rt cookie (HTTP-only)
→
Return accessToken + csrfToken

3.4 Protected Request Flow (3-Step Middleware)

Request arrives
→
Step 1: Verify JWT signature & expiry
→
Step 2: Find session by session_id → is_valid? not expired?
→
Step 3: Is user active in DB?
→
CSRF: x-csrf-token header matches session?
→
Controller runs

Any step failing returns 401 or 403. The 3 DB checks per request is the main scalability bottleneck — see Section 10.

Koi bhi step fail ho toh 401 ya 403 milta hai. Har request pe 3 DB calls — ye scalability bottleneck hai, Section 10 dekho.

3.5 Refresh Flow (Silent Re-Auth)

Access token expired (401)
→
Browser auto-sends rt cookie to /auth/refresh
→
Hash received token → find session in DB
→
Invalidate old session → create new session
→
Return new accessToken + csrfToken
→
Set new rt cookie

3.6 Logout Flow

Auth + CSRF middleware pass
→
Set session is_valid = false in DB
→
Clear rt cookie (maxAge=0)
→
200 OK

Result: Even if someone has a copy of the old access token, Step 2 of auth middleware rejects it instantly because the session is now is_valid=false.

Result: Kisi ke paas purana access token bhi ho toh kaam nahi karega, kyunki DB mein session invalid ho chuka hai.

4. v2.1 Changes — What We Fixed and Why NEW 4. v2.1 mein Kya Fix Kiya aur Kyun NAYA

After deploying v2.0, the frontend dev reported that /auth/refresh returned 401 "Refresh token is required" when called from localhost:5173 to api.succesly.in. Three bugs were found and fixed.

v2.0 deploy karne ke baad, frontend se report aaya ki /auth/refresh pe 401 aa raha hai jab localhost:5173 se api.succesly.in ko call karte hain. Teen bugs mile aur fix kiye.

Bug 1 — SameSite=None Requires Secure=true

Root Cause

The original code set secure: process.env.NODE_ENV === 'production' as a module-level constant. On the deployed server, NODE_ENV=development (dev .env was used). So secure: false was sent. Browsers reject SameSite=None without Secure=true, so the rt cookie was silently dropped — never stored in the browser.

Purana code secure: NODE_ENV === 'production' use karta tha. Server pe NODE_ENV=development tha (dev .env). Toh secure: false jata tha. Browsers SameSite=None ko Secure=true ke bina reject karte hain — rt cookie store hi nahi hoti thi.

Fix — Per-Request Cookie Options

Cookie options are now computed per-request by reading the actual connection type, not NODE_ENV:

Cookie options ab har request pe actual connection type dekh ke decide hoti hai, NODE_ENV se nahi:

function buildCookieOptions(req) {
  const isHttps = req.secure || req.headers['x-forwarded-proto'] === 'https';
  return {
    httpOnly: true,
    secure:   isHttps,                         // true on real HTTPS
    sameSite: isHttps ? 'none' : 'lax',      // none+secure on HTTPS, lax on local
    maxAge:   7 * 24 * 60 * 60 * 1000,
    path:     '/api/v1/auth',                 // scope to auth routes only
  };
}

Why SameSite=None? The frontend (localhost:5173 or succesly.in) is a different origin from the API (api.succesly.in). Browsers block cookies on cross-origin requests unless SameSite=None; Secure is set. SameSite=None MUST be paired with Secure=true — the browser rejects it otherwise.

SameSite=None kyun? Frontend (localhost:5173 ya succesly.in) aur API (api.succesly.in) alag origins hain. Cross-origin requests pe browser cookies block karta hai jab tak SameSite=None; Secure na ho.

Bug 2 — Express Didn't Know the Request Was HTTPS

Root Cause

The server runs behind nginx/Caddy (reverse proxy). The proxy terminates HTTPS and forwards requests to Express as plain HTTP internally. Express saw the internal HTTP connection and set req.secure = false, even though the original request was HTTPS.

Server nginx ke peeche hai. Nginx HTTPS terminate karta hai aur Express ko plain HTTP bhejta hai. Express dekhta tha HTTP connection, toh req.secure = false hota tha — chahe real request HTTPS ho.

Fix — Trust Proxy in app.ts

// app.ts — BEFORE helmet, BEFORE cors, first line
app.set('trust proxy', 1);
// Now Express reads X-Forwarded-Proto from nginx
// req.secure = true when real connection was HTTPS

With this set, req.secure correctly reflects the real protocol. The buildCookieOptions function then returns SameSite=None; Secure=true on production, and SameSite=Lax; Secure=false on local HTTP.

Is ke baad req.secure sahi protocol reflect karta hai. Production pe SameSite=None; Secure=true, local pe SameSite=Lax; Secure=false.

Bug 3 — Swagger Wasn't Showing /refresh and /logout

Fix

The auth.swagger.ts file was never updated after adding the new endpoints. The full file was rewritten to include all 4 auth endpoints with correct schemas, cookie parameter on /refresh, and CSRF header on /logout.

auth.swagger.ts update nahi hua tha. Poora file rewrite kiya — sabhi 4 endpoints, cookie parameter refresh pe, CSRF header logout pe.

Also added withCredentials: true to Swagger UI options in app.ts so the rt cookie is sent when you click "Execute" in Swagger.

app.ts mein withCredentials: true add kiya Swagger UI ke liye — ab Swagger mein "Execute" karne pe rt cookie automatically send hoti hai.

7. Backend Developer Guide — Adding New Routes 7. Backend Developer Guide — Naye Routes Kaise Banao

7.1 New Protected Route — Standard Pattern

// src/routes/your-feature/your.routes.ts
import { Router } from 'express';
import { authMiddleware, csrfMiddleware } from '../../middlewares';
import { apiKeyMiddleware } from '../../middlewares/api-key.middleware';
import * as YourController from '../../controllers/your.controller';
import { requirePermission } from '../../middlewares/permission.middleware';

const router = Router();

// Apply auth + CSRF + API key to ALL routes in this file
router.use(authMiddleware, csrfMiddleware, apiKeyMiddleware);

// GET — no CSRF header needed on reads, but auth still runs
router.get('/', requirePermission('moduleId', 'read'), YourController.getAll);

// POST — CSRF token REQUIRED in x-csrf-token header
router.post('/', requirePermission('moduleId', 'create'), YourController.create);

export default router;

7.2 Checklist for Every New Protected Route

  • Add router.use(authMiddleware, csrfMiddleware) at the top of the router file
  • Register the router in src/routes/index.ts
  • If the route needs an API key, also add apiKeyMiddleware
  • Add a Swagger definition in a *.swagger.ts file — include the bearerAuth security and x-csrf-token parameter
  • Add the Swagger spec to the main swagger config
  • Test in Swagger: login first, copy csrfToken, paste in x-csrf-token header, call the endpoint

7.3 Common Mistakes to Avoid

MistakeConsequenceCorrect Approach
Forgetting csrfMiddleware on a routerPOST routes are CSRF-vulnerableAlways: router.use(authMiddleware, csrfMiddleware)
Storing refresh token raw in DBIf DB leaked, tokens can be used directlyAlways store SHA-256 hash: crypto.createHash('sha256').update(token).digest('hex')
Hard-coding cookie secure: falseSameSite=None rejected by browsersAlways use buildCookieOptions(req) from auth.controller
Putting session_id in access token then not checking DBLogout has no effect on active tokensStep 2 of authMiddleware MUST query MongoDB for session
Adding a new origin to CORS without thinkingUnintended domains can send credentialed requestsOnly add origins that your team controls

8.1 Where to Store What — Storage Diagram

✅ JS Memory (Variable)
Store here:
accessToken
csrfToken

Why: Extensions can't read variables. Cleared on page refresh (intentional — use /auth/refresh to restore).
🍪 HTTP-only Cookie (Browser-managed)
Stored automatically by browser:
rt (refresh token)

You cannot read or write this from JS. Browser sends it automatically to /api/v1/auth/* routes. Do NOT touch this.
❌ localStorage / sessionStorage
NEVER store tokens here.

Why: Any JavaScript on the page (ads, extensions, XSS) can read localStorage. It persists across browser restarts — a stolen token lasts forever.
Key Insight for Freshers

When the user closes the tab or refreshes the page, your JS variables are cleared — that's by design. On the next page load, call /auth/refresh with the rt cookie (browser sends it automatically) to silently get a new accessToken + csrfToken. The user won't see a login screen unless their session truly expired (7 days of inactivity).

Jab user page refresh kare ya tab close kare, JS variables clear ho jaate hain — yahi design hai. Next page load pe /auth/refresh call karo (rt cookie browser automatic bhejta hai) — silently naya accessToken + csrfToken milega. User ko login screen nahi dikhega jab tak session truly expire na ho (7 din ki inactivity).

What Goes in Redux / Zustand?

8.2 Auth Store with Zustand (Recommended)

// src/store/authStore.ts
import { create } from 'zustand';

interface AuthState {
  accessToken: string | null;
  csrfToken:   string | null;
  user:        { user_id: string; email: string; role_id: string } | null;
  isAuthenticated: boolean;
  setAuth: (accessToken: string, csrfToken: string, user: any) => void;
  clearAuth: () => void;
}

export const useAuthStore = create<AuthState>((set) => ({
  accessToken:     null,
  csrfToken:       null,
  user:            null,
  isAuthenticated: false,

  setAuth: (accessToken, csrfToken, user) =>
    set({ accessToken, csrfToken, user, isAuthenticated: true }),

  clearAuth: () =>
    set({ accessToken: null, csrfToken: null, user: null, isAuthenticated: false }),
}));

8.3 Login Page Integration

// src/pages/Login.tsx (simplified)
import { useAuthStore } from '../store/authStore';
import { apiClient }   from '../api/apiClient';
import { useNavigate } from 'react-router-dom';

export function LoginPage() {
  const setAuth   = useAuthStore(s => s.setAuth);
  const navigate  = useNavigate();

  async function handleLogin(email: string, password: string) {
    const res = await apiClient.post('/auth/login', { email, password });
    const { accessToken, csrfToken, user } = res.data.data;

    setAuth(accessToken, csrfToken, user);   // store in memory
    // rt cookie is set automatically by the browser — you don't touch it

    navigate('/dashboard');
  }
}
Important for Freshers

Notice we never write localStorage.setItem('token', ...). The setAuth() call stores in Zustand (JS memory). If the user refreshes the page, this state clears — but the rt cookie stays. The App component handles this via /auth/refresh on mount (see Section 8.6).

localStorage.setItem('token', ...) kabhi mat likho. setAuth() Zustand (JS memory) mein store karta hai. Page refresh pe ye clear hoga — but rt cookie rahegi. App component /auth/refresh call karega mount pe (Section 8.6 dekho).

8.4 Axios Client + Silent Refresh Interceptor

This is the most important piece. The interceptor automatically:

Ye sabse important part hai. Interceptor automatically:

  • Attaches Authorization + x-csrf-token headers to every request
  • Har request pe Authorization + x-csrf-token header attach karta hai
  • Detects 401 "Token has expired" → calls /auth/refresh → retries the original request
  • 401 "Token has expired" detect karta hai → /auth/refresh call karta hai → original request retry karta hai
  • If refresh fails → clears auth state → redirects to login
  • Refresh fail ho toh → auth state clear karta hai → login page pe bhejta hai
// src/api/apiClient.ts
import axios from 'axios';
import { useAuthStore } from '../store/authStore';

const BASE_URL = 'https://api.succesly.in/api/v1';

export const apiClient = axios.create({
  baseURL:         BASE_URL,
  withCredentials: true,   // CRITICAL — sends rt cookie cross-origin
});

// REQUEST: attach tokens to every outgoing request
apiClient.interceptors.request.use((config) => {
  const { accessToken, csrfToken } = useAuthStore.getState();
  if (accessToken) {
    config.headers['Authorization'] = `Bearer ${accessToken}`;
  }
  if (csrfToken && ['post','put','patch','delete'].includes(config.method!)) {
    config.headers['x-csrf-token'] = csrfToken;
  }
  return config;
});

let isRefreshing = false;
let waitQueue: Array<(token: string) => void> = [];

// RESPONSE: catch 401 → refresh → retry
apiClient.interceptors.response.use(
  (res) => res,
  async (error) => {
    const original = error.config;
    if (error.response?.status !== 401 || original._retry) return Promise.reject(error);

    original._retry = true;

    if (isRefreshing) {
      return new Promise((resolve) => {
        waitQueue.push((token) => {
          original.headers['Authorization'] = `Bearer ${token}`;
          resolve(apiClient(original));
        });
      });
    }

    isRefreshing = true;
    try {
      const { data } = await apiClient.post('/auth/refresh');
      const { accessToken, csrfToken } = data.data;
      useAuthStore.getState().setAuth(accessToken, csrfToken, useAuthStore.getState().user!);
      waitQueue.forEach((cb) => cb(accessToken));
      waitQueue = [];
      original.headers['Authorization'] = `Bearer ${accessToken}`;
      return apiClient(original);
    } catch {
      useAuthStore.getState().clearAuth();
      window.location.href = '/login';
      return Promise.reject(error);
    } finally {
      isRefreshing = false;
    }
  }
);
Why withCredentials: true?

Without this, the browser won't send the rt cookie on cross-origin requests to api.succesly.in. This MUST be set on the axios instance. The backend's CORS also has credentials: true to match.

Iske bina browser rt cookie cross-origin requests pe send nahi karega. Ye axios instance pe MUST set hona chahiye. Backend ka CORS bhi credentials: true set hai.

Secure Auth v2.1Section 8 · Frontend Do's & Don'ts

8.8 Do's and Don'ts for Freshers

✅ DO These

  • Store accessToken and csrfToken in Zustand (JS memory only)
  • Always set withCredentials: true on your axios instance
  • Call /auth/refresh on every app startup (page load)
  • Send x-csrf-token header on all POST, PUT, PATCH, DELETE requests
  • Use the response interceptor pattern to silently refresh on 401
  • Show a loading screen while checking session on startup
  • Call /auth/logout before clearing local state (server must invalidate)
  • Handle 403 from CSRF separately — usually means csrfToken is stale (call refresh)

❌ NEVER DO These

  • localStorage.setItem('accessToken', ...) — XSS vulnerability
  • document.cookie = 'rt=...' — HTTP-only cookies can't be set from JS
  • Decode the JWT with atob() to get user info — use /auth/profile or store user from login response
  • Check for cookie existence to decide if user is logged in — check Zustand isAuthenticated
  • Call /auth/refresh in a loop on failure — check isRefreshing flag first
  • Forget withCredentials on the base axios instance — the rt cookie won't be sent
  • Store the refresh token anywhere in JS — you literally can't (HTTP-only)
  • Skip the CSRF header on any mutation — you'll get 403 on every write request

Quick Checklist — Before Shipping Frontend

  • Axios instance has withCredentials: true and baseURL = 'https://api.succesly.in/api/v1'
  • Request interceptor attaches Authorization: Bearer <accessToken> to every request
  • Request interceptor attaches x-csrf-token: <csrfToken> to POST/PUT/PATCH/DELETE
  • Response interceptor handles 401 → calls /auth/refresh → retries failed request
  • App.tsx calls /auth/refresh on mount to restore session after page refresh
  • ProtectedRoute shows loading state while session is being checked
  • Login stores { accessToken, csrfToken, user } in Zustand, navigates to dashboard
  • Logout calls /auth/logout API, then clears Zustand state, then redirects to /login
  • No tokens stored in localStorage, sessionStorage, or readable cookies
  • Tested on localhost:5173 → api.succesly.in (cross-origin): login sets rt cookie, refresh sends rt cookie

Secure Auth v2.1Section 9 · Merits & Demerits

9. Merits & Demerits — Honest Assessment 9. Fayde aur Nuksan — Sachchi Baat

This is a genuine assessment, not marketing. Every system has tradeoffs.

Ye honest assessment hai, koi marketing nahi. Har system mein tradeoffs hote hain.

Merits (What's Good)
  • Cookie theft is impossible: Refresh token is in an HTTP-only cookie. JavaScript — including malicious extensions — cannot read it under any circumstances.
  • Cookie forgery is impossible: A manually-set fake cookie has no matching server-side session. The backend rejects it at Step 2 of auth middleware.
  • Instant logout works: Logout sets is_valid=false in DB. Old access tokens are rejected within milliseconds, not 15 minutes.
  • CSRF protection is real: Uses crypto.timingSafeEqual — immune to timing attacks. Token is in memory, not a cookie, so forged cross-site requests can never include it.
  • Refresh token rotation: Each refresh call creates a new session and invalidates the old one. A stolen refresh token can only be used once.
  • Clean architecture: Auth logic separated into controller → use-case → repository layers. Easy to test or swap storage layer.
  • Per-request cookie options: Works correctly on both HTTP (local dev) and HTTPS (production) without changing environment variables.
  • TTL index cleanup: MongoDB auto-deletes expired sessions. No manual cron job needed.
Demerits (Honest Gaps)
  • 2–3 DB queries per request: Step 2 queries sessions collection, Step 3 queries users collection. At high traffic (1000 req/s), MongoDB becomes the bottleneck. No caching.
  • Single session only: There is no per-device session management. User can't see "logged in on 3 devices" or selectively logout from one device.
  • No rate limiting: /auth/login and /auth/refresh have no rate limiting. A bot can try 10,000 password combinations. This is a real gap.
  • No refresh token reuse detection: If an attacker gets the refresh token and uses it before the real user, the real user's refresh will fail — but there's no alert or suspicious activity log.
  • Access token can't be revoked before 15 min: On logout, the session is invalidated (which blocks the token via DB check), but if Step 2 is ever skipped accidentally, old access tokens work for 15 minutes.
  • No 2FA support: Password-only authentication. A compromised password = compromised account.
  • HS256 JWT: Symmetric signing means the same key signs and verifies. If the key leaks, any service can forge tokens. RS256 (asymmetric) is better for microservices.
  • No audit log: No record of login attempts, IP changes, or suspicious activity.

Secure Auth v2.1Section 11 · Future Roadmap

11. Future Roadmap 11. Aage Kya Karna Hai

Prioritized by impact. Items marked Security should be added before significant user growth.

Impact ke hisaab se priority. Security mark wale items user growth se pehle add karne chahiye.

Priority 1 — Rate Limiting Security
Add express-rate-limit on /auth/login (e.g. max 10 attempts per 15 min per IP) and /auth/refresh (max 30/min). Without this, a bot can run unlimited password-guessing attacks. 1 hour of work.
/auth/login pe rate limit lagao (10 attempts per 15 min per IP). Bina is ke bot unlimited password guessing kar sakta hai. 1 ghante ka kaam.
Priority 2 — Refresh Token Reuse Detection Security
When a refresh token is used twice (stolen + reused), the second use should revoke ALL sessions for that user (token family invalidation). Currently the second use just fails — the attacker might already have a new valid session from the first use.
Agar refresh token 2 baar use ho (chori ke baad), toh us user ke SAARE sessions revoke kar do. Abhi second use fail hota hai lekin attacker pehli use se new session le chuka hoga.
Priority 3 — Redis Session Store Performance
Replace MongoDB session lookup with Redis for auth middleware Step 2. Reduces per-request auth overhead from ~10ms to ~0.5ms. Required before scaling beyond 2,000 concurrent users.
Auth middleware Step 2 mein MongoDB ki jagah Redis. Per-request auth overhead 10ms se 0.5ms ho jaayega. 2,000 concurrent users se pehle zaroori hai.
Priority 4 — Multi-Device Session Management Feature
Show user a list of active sessions (device, IP, last seen). Let them logout from specific devices. This requires storing device info per session (already partially done — user_agent and ip_address stored).
User ko active sessions ki list dikhaao (device, IP, last seen). Specific device se logout karne do. Device info already store ho raha hai (user_agent, ip_address).
Priority 5 — Two-Factor Authentication Security+
Add TOTP (Google Authenticator) or email OTP as second factor on login. Login flow becomes: verify password → generate temp token → user verifies OTP → issue real access/refresh tokens. Session model needs an is_2fa_verified flag.
Login ke baad Google Authenticator ya email OTP se verify karo. Password verify → temp token → OTP verify → real tokens. Session model mein is_2fa_verified flag chahiye.
Priority 6 — RS256 JWT (Asymmetric Signing) Architecture
Replace HS256 (one shared secret) with RS256 (private key signs, public key verifies). Important if multiple services need to verify tokens — they only need the public key, not the secret. Low priority unless moving to microservices.
HS256 (shared secret) ko RS256 se replace karo (private key se sign, public key se verify). Multiple services ke liye useful — unhe sirf public key chahiye. Microservices nahi hain toh low priority.
Priority 7 — Audit Logging Compliance
Log all auth events: login success/failure, refresh, logout, IP address, device, timestamp. Store in a separate audit_logs collection. Required for SOC2/compliance and for detecting account takeover attempts.
Sabhi auth events log karo: login, refresh, logout, IP, device, time. Alag audit_logs collection mein. SOC2/compliance ke liye zaroori.
